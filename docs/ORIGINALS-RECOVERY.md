## Syntax-repair policy

After conversion/criticism settle for a unit, a failed selected version receives
the applicable established deterministic repair first. Existing compiler
dependency recovery remains separate. Unknown assets/environment failures do not
become requests to delete content or install arbitrary dependencies.

If a precise TeX-content error remains, at most one Low request may be reserved
for its immutable version lineage, with 8192 completion tokens including reasoning.
The request includes the first substantive compiler error, surrounding lines,
preamble and necessary macro definitions. It asks for strict old/new JSON edits,
not a rewritten paper. Existing fenced-JSON/schema handling parses the response.

Validation requires unique anchors inside the declared error/macro spans, bounded
nonoverlapping edits, unchanged asset references, and allowlisted syntax operations:
unchanged mathematical fragments wrapped in missing delimiters, the established
texttt wrapper correction, or paragraph-capable scoped colour declarations.
Changes to expressions, signs, bounds, indices, numbers, prose, annotations or
assets are rejected. Existing mathematics and verbatim/code are protected.
Ambiguous or unsupported repairs stay unresolved. A candidate is selected only
after its isolated build passes; failed candidates and patches remain recorded.

`syntax_lineages` plus sealed per-task plans and durable reservations prevent
derivatives or resumes from resetting the one-request allowance. HTTP workers
only write their own call evidence. The coordinator validates, compiles, selects
and publishes, and adds eligible repair tasks to that same scheduler. A document's
failed/rejected patch does not stop independent documents. Shared integrity,
ownership, transport or compiler infrastructure faults still stop admission.
